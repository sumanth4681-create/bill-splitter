What it is

A local proof of concept: photograph a group receipt, let one person claim items on behalf of each friend, and see what everyone owes the payer. Shared items are split only among the people who had them; unclaimed items, tax, and tip are split across everyone; the amounts always add up to the receipt total.

Four pieces, each with a fixed input and output shape:

PieceWhereJob
Screenbill-splitter/frontend/app.pyStreamlit tabs (Upload, History) and the bill view. No math, no storage; it only calls the API.
Backendbill-splitter/backend/main.pyFastAPI endpoints. Every change returns the full bill with a freshly computed summary.
Readersbackend/ocr.py, backend/ocr_local.pyGoogle Document AI or a local LM Studio vision model, behind one function read_receipt(). Responses are saved by image hash and replayed for free.
Split mathbackend/split.pyPure function compute_split(): items, people, claims in; each person's share out. Integer cents only.
Storagebackend/storage.pySQLite file data/bills.db: bills, items, people, claims.

One action, end to end: ticking an item for a person

Reference route (three stops)

Not toured live; the practice in this project went into the agent passes instead. Use it when you need to find where a behaviour lives.

1. Entry: bill-splitter/frontend/app.py → items_section() draws one checkbox per item for the selected person; its on_change is toggle_claim(), which calls api_client.set_claim() and shows a toast.
2. Logic and storage: bill-splitter/backend/main.py → put_claim() checks the item and person belong to this bill (404 otherwise), then storage.set_claim() inserts or deletes one row in claims. The summary is never stored: _summary() calls split.compute_split() on every response.
3. Result: bill-splitter/backend/split.py → compute_split(). Rule by rule: a claimed item is divided among its claimers (fair_divide rotates leftover cents), an unclaimed item among everyone, tax and tip among everyone, a discount subtracted, and any gap to the receipt total shared as difference_cents so totals always equal what was paid.

Added after the first snapshot: the share link

A friend's door into the same bill. backend/storage.py · bill_id_for_token() turns the link's token into a bill id; backend/main.py · get_shared_bill / put_shared_claim serve the bill and accept ticks through _apply_claim, the same code the payer's route uses; frontend/app.py · shared_page() is the phone page and share_section() draws the link and QR code. Written by the project owner with review; tests in tests/test_api.py and tests/test_share_page.py.

To change this, start here

  • Split rules (proportional tax, who gets the extra cent): backend/split.py, then run tests/test_split.py; the property test there must still pass.
  • Which fields a reader returns (quantity, discounts): backend/ocr.py · map_expense_document() for Google, backend/ocr_local.py · map_local_response() and SYSTEM_PROMPT for the local model. Saved responses in backend/fixtures/ let you test without paying or waiting.
  • Screen text and layout: frontend/app.py; palette in .streamlit/config.toml.
  • Limits (upload size, max cents, name lengths): the constants at the top of backend/main.py.
  • A new endpoint: add the storage function, the Pydantic body model, the route in main.py, a wrapper in frontend/api_client.py, and a case in tests/test_api.py.

A practice to reuse

Give agents a narrow brief, no edit rights, and a disposable target; then re-verify every claim yourself. In this project three subagents ran in parallel against a copy of the API on a scratch database: a black-box attacker, a white-box reviewer, and a fuzzer for the pure functions. The reviewer found the bug that mattered most (saved Google responses embedded the receipt photo, so the redaction in ocr.strip_sensitive was cosmetic); the fuzzer found parser crashes and a filter that dropped real items. Each finding was reproduced by hand before any fix, and each fix got a regression test (tests/ grew from 44 to 59). The same pattern works on any codebase: different vantage points find different bugs, and verification, not trust, is what makes delegation safe.

Earlier instance of the same idea

backend/split.py and its tests were written by a subagent that saw only two spec sections (Split Logic and Contracts in devpost/spec.md). All tests passed first run, and the gaps it reported (the receipt total missing from the signature, an unstated overrides type) were exactly where the contract was silent.
